## Consent-safe hosted probe

\`scripts/hosted_acceptance.py\` performs non-destructive checks and deliberately does not persist:

- bearer tokens;
- passwords or OTPs;
- admin cookie values;
- profile/email/private notification bodies;
- arbitrary authenticated response bodies.

Run its local parser/privacy self-test:

\`\`\`bash
python scripts/hosted_acceptance.py self-test
\`\`\`

Run public monitoring plus optional authorized test-user API checks:

\`\`\`bash
export ATHAR_HOSTED_BEARER_TOKEN="<short-lived authorized test-user token>"

python scripts/hosted_acceptance.py probe \
  --api-base https://api.example.org/api/v1/ \
  --site-base https://example.org/ \
  --samples 10 \
  --output docs/deployment/results/hosted-smoke.json

unset ATHAR_HOSTED_BEARER_TOKEN
\`\`\`

The bearer token remains only in process environment and is never emitted to evidence.

The probe validates:

- HTTPS-only clean base URLs;
- TLS hostname verification and public certificate SHA-256;
- \`GET /api/v1/health\` contract, unique request ids and repeated timing;
- public site HTML availability;
- Admin login page availability and security-cookie attribute presence without storing the cookie;
- when an authorized bearer exists: \`/me/profile\`, notification preferences and a one-row inbox page, recording only status/timing/content type.

The current health contract is intentionally small: API version plus \`available\`. A successful request still exercises the deployed API bootstrap; monitoring must not expose database names, provider secrets, user counts, email addresses or private worship/activity data.

## Admin acceptance

Admin authentication is a dedicated cookie-session boundary. Do not place an Admin session cookie in the automated evidence probe.

On an authorized browser session, record only redacted evidence that proves:

1. unauthenticated \`/admin\` redirects to login;
2. authorized Admin/Owner can login;
3. non-Admin is denied;
4. CSRF-protected mutations reject missing/invalid CSRF;
5. one approved staging CRUD journey creates an audit/revision trail;
6. logout invalidates the Admin session;
7. Arabic/English and light/dark shell still work.

Do not perform destructive production CRUD for acceptance. Use staging/approved disposable content.

## Recoverable rollout

Before changing production:

1. record pushed git SHA, release version code/name, APK/AAB SHA-256 and signer certificate fingerprint;
2. verify a current encrypted backup and managed-asset manifest according to \`BACKUP_AND_RECOVERY.md\`;
3. retain the previously deployed server artifact/config reference outside public document root;
4. confirm migrations and rollback compatibility before applying schema changes;
5. deploy server, run public hosted probe, then authenticated test-user smoke;
6. only then expose the signed Android release to the approved rollout channel.

Rollback trigger examples: health failure, authentication/session breakage, owner-scope/privacy failure, corrupt backup/restore, release signature/package mismatch or critical device crash.

Rollback rules:

- stop/hold Android rollout first;
- restore the previous server artifact/config when schema remains compatible;
- if a migration changed stored data incompatibly, use the approved encrypted backup/staging-rehearsed recovery procedure rather than improvising down-migrations;
- never reuse/revoke signing keys as a normal rollback mechanism;
- versionCode remains monotonic; a corrected Android build receives a higher versionCode.

After rollback, rerun the hosted probe and the affected authorized-device journey before resuming rollout.
